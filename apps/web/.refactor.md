> **Purpose:** Complete reference for an AI agent to refactor this inventory/sales management project.
> Covers `proxy.ts`, folder structure, permissions, DAL, and TanStack Query integration patterns.

## 1. What Changed — middleware.ts → proxy.ts

Next.js 16 replaces `middleware.ts` with `proxy.ts`. It is **not just a rename** — it signals a clearer architectural contract:

- Rename the file: `middleware.ts` → `proxy.ts`
- Rename the export: `export function middleware()` → `export function proxy()`
- Everything else (matcher config, NextRequest/NextResponse) stays the same
- You can run the official codemod: `npx @next/codemod middleware-to-proxy`

**Critical rule (unchanged from middleware):** `proxy.ts` runs on the Edge Runtime. It **cannot** access PostgreSQL, Prisma, or any Node.js-only API. It is for **thin, cookie-existence checks only**. All real auth and role enforcement happens in `layout.tsx` and the DAL.

## 2. The 3-Layer Security Architecture

```
REQUEST
  │
  ▼
┌─────────────────────────────────────────────────────┐
│  LAYER 1: proxy.ts (Edge Runtime)                   │
│  Q: Does a session cookie exist at all?             │
│  → No cookie → redirect /login                      │
│  → Cookie present → NextResponse.next()             │
│  ⚠ Does NOT verify role. Does NOT validate session. │
└─────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────┐
│  LAYER 2: layout.tsx (Node.js, Server Component)    │
│  Q: Is the session valid? Is the role allowed here? │
│  → Calls auth.api.getSession() — real DB lookup     │
│  → Wrong role → redirect /dashboard                 │
│  → No session → redirect /login                     │
└─────────────────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────────────────┐
│  LAYER 3: lib/dal.ts + Server Actions + API Routes  │
│  Q: Before touching any data, is this caller        │
│     authenticated and authorized?                   │
│  → requireRole() called inside every mutation       │
│  → Never trusts what the client sends               │
└─────────────────────────────────────────────────────┘
```

**Why 3 layers?** CVE-2025-29927 proved that relying solely on `proxy.ts`/middleware for auth is catastrophically insecure. The DAL pattern (Layer 3) is now the canonical Next.js security model.

## 3. Layer 1 — `proxy.ts`

```ts
// proxy.ts (project root, same level as /app)
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'
import { getSessionCookie } from 'better-auth/cookies'

const protectedRoutes = [
  '/dashboard',
  '/pos',
  '/sales',
  '/products',
  '/categories',
  '/inventory',
  '/suppliers',
  '/purchase-orders',
  '/customers',
  '/credits',
  '/reports',
  '/notifications',
  '/settings',
]

const authRoutes = ['/login', '/register']

// Named export — this is required in Next.js 16
export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl

  // getSessionCookie() only checks cookie existence — Edge-safe, no DB call
  const sessionCookie = getSessionCookie(request)

  const isProtected = protectedRoutes.some(r => pathname.startsWith(r))
  const isAuthRoute  = authRoutes.some(r => pathname.startsWith(r))

  if (isProtected && !sessionCookie) {
    return NextResponse.redirect(new URL('/login', request.url))
  }

  if (isAuthRoute && sessionCookie) {
    return NextResponse.redirect(new URL('/dashboard', request.url))
  }

  return NextResponse.next()
}

export const config = {
  matcher: [
    /*
     * Match all paths EXCEPT:
     * - _next/static (static files)
     * - _next/image (image optimization)
     * - favicon.ico
     * - api/auth (better-auth handler)
     * - public files (png, jpg, svg, etc.)
     */
    '/((?!_next/static|_next/image|favicon.ico|api/auth|.*\\.(?:png|jpg|jpeg|gif|svg|ico|webp)$).*)',
  ],
}
```

### 4a. Root Dashboard Layout (all authenticated users)

```ts

import { headers } from 'next/headers'
import { redirect } from 'next/navigation'
import { DashboardShell } from '@/components/shared/DashboardShell'

  children,

  return (
    <RoleProvider role={session.user.role} user={session.user}>

    </RoleProvider>
```

### 4b. Role-Gated Layout Pattern

Apply this pattern to any route group that restricts by role:

```ts
// app/(dashboard)/settings/layout.tsx        → OWNER only
// app/(dashboard)/reports/layout.tsx         → OWNER + MANAGER
// app/(dashboard)/suppliers/layout.tsx       → OWNER + MANAGER
// app/(dashboard)/purchase-orders/layout.tsx → OWNER + MANAGER

import { auth } from '@/lib/auth'
import { headers } from 'next/headers'
import { redirect } from 'next/navigation'

const ALLOWED_ROLES = ['OWNER'] // change per route

export default async function Layout({ children }: { children: React.ReactNode }) {
  const session = await auth.api.getSession({ headers: await headers() })

  if (!session || !ALLOWED_ROLES.includes(session.user.role)) {
    redirect('/dashboard')
  }

  return <>{children}</>
}
```

## 5. Layer 3 — `lib/dal.ts` (Data Access Layer)

This is the **real security boundary**. Every server action and API route calls these helpers before touching data.

```ts
// lib/dal.ts
import 'server-only' // prevents accidental client-side import
import { auth } from '@/lib/auth'
import { headers } from 'next/headers'
import { redirect } from 'next/navigation'
import { cache } from 'react'
import type { UserRole } from '@/generated/prisma'

/**
 * getSession()
 * Memoized with React cache() — only hits DB once per render tree.
 * Redirects to /login if no valid session exists.
 */
export const getSession = cache(async () => {
  const session = await auth.api.getSession({ headers: await headers() })
  if (!session) redirect('/login')
  return session
})

/**
 * requireRole(...roles)
 * Ensures the current user has one of the specified roles.
 * Redirects to /unauthorized if not.
 */
export const requireRole = cache(async (...roles: UserRole[]) => {
  const session = await getSession()
  if (!roles.includes(session.user.role as UserRole)) {
    redirect('/unauthorized')
  }
  return session
})

// ── Convenience helpers matching your schema roles ──────────────────────────

/** OWNER only */
export const requireOwner = () => requireRole('OWNER')

/** OWNER or MANAGER */
export const requireManager = () => requireRole('OWNER', 'MANAGER')

/** Any authenticated user */
export const requireAny = () => requireRole('OWNER', 'MANAGER', 'CASHIER')

/**
 * getCurrentBusiness()
 * Returns the businessId of the session user.
 * Throws if no session or no business attached.
 */
export const getCurrentBusiness = cache(async () => {
  const session = await getSession()
  if (!session.user.businessId) redirect('/onboarding')
  return session.user.businessId
})
```

```ts
  'reports:full':             ['OWNER'],
  'reports:limited':          ['MANAGER'],

  // ── Staff & Settings ────────────────────────────────────────────
  'staff:manage':             ['OWNER'],
  'staff:invite':             ['OWNER'],
  'settings:manage':          ['OWNER'],
  'audit-logs:view':          ['OWNER'],

  // ── Notifications ───────────────────────────────────────────────
  'notifications:view:own':   ['OWNER', 'MANAGER', 'CASHIER'],
} as const

export type Permission = keyof typeof PERMISSIONS

/**
 * Check if a role has a specific permission.
 * Used in Server Components, layouts, and client UI gating.
 */
export function hasPermission(role: UserRole, permission: Permission): boolean {
  return (PERMISSIONS[permission] as readonly string[]).includes(role)
}

/**
 * Check if a role has ANY of the listed permissions.
 * Useful for compound access checks.
 */
export function canAny(role: UserRole, permissions: Permission[]): boolean {
  return permissions.some(p => hasPermission(role, p))
}
```

## 7. Server Actions — Always Re-verify

Server actions are the mutation layer. Every action calls `requireRole()` or a convenience helper **before** doing anything. The `businessId` and `userId` always come from the session — never from the client.

```ts
// actions/sales.ts
'use server'
import { requireAny, requireManager, getSession } from '@/lib/dal'
import { prisma } from '@/lib/db'
import { revalidatePath } from 'next/cache'

export async function createSale(data: CreateSaleInput) {
  const session = await requireAny() // All roles can create sales

  const sale = await prisma.sale.create({
    data: {
      ...data,
      cashierId: session.user.id,          // Always from session
      businessId: session.user.businessId!, // Always from session
    },
  })

  revalidatePath('/sales')
  return sale
}

export async function voidSale(saleId: string) {
  const session = await requireManager() // CASHIER cannot void

  await prisma.sale.update({
    where: {
      id: saleId,
      businessId: session.user.businessId!, // Scoped to business
    },
    data: { status: 'VOID' },
  })

  revalidatePath('/sales')
}
```

```ts
// lib/query-client.ts
import { QueryClient } from '@tanstack/react-query'
import { cache } from 'react'

// cache() ensures ONE QueryClient per server request — never shared across users
export const getQueryClient = cache(
```

### 9d. Server Prefetch + HydrationBoundary Pattern

This is the canonical pattern for every page that needs data. The Server Component prefetches the data; the Client Component consumes it with `useQuery()` instantly — no loading spinner.

```tsx
// app/(dashboard)/products/page.tsx  (Server Component)
import { HydrationBoundary, dehydrate } from '@tanstack/react-query'
import { getQueryClient } from '@/lib/query-client'
import { getSession } from '@/lib/dal'
import { prisma } from '@/lib/db'
import { ProductsClient } from '@/components/features/products/ProductsClient'

export default async function ProductsPage() {
  const session = await getSession()
  const queryClient = getQueryClient()

  // Prefetch on the server — no loading state on client
  await queryClient.prefetchQuery({
    queryKey: ['products', session.user.businessId],
    queryFn: () =>
      prisma.product.findMany({
        where: { businessId: session.user.businessId!, isActive: true },
        include: { category: true, stockRecord: true },
        orderBy: { createdAt: 'desc' },
      }),
  })

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <ProductsClient role={session.user.role} />
    </HydrationBoundary>
  )
}
```

```tsx
// components/features/products/ProductsClient.tsx  (Client Component)
'use client'
import { useQuery } from '@tanstack/react-query'
import { hasPermission } from '@/lib/permissions'
import type { UserRole } from '@/generated/prisma'

interface Props {
  role: UserRole
}

export function ProductsClient({ role }: Props) {
  // Data is already in cache from server prefetch — renders instantly
  const { data: products } = useQuery({
    queryKey: ['products'],
    queryFn: async () => {
      const res = await fetch('/api/products')
      return res.json()
    },
  })

  const canCreate = hasPermission(role, 'products:create')
  const canEdit   = hasPermission(role, 'products:edit')
  const canDelete = hasPermission(role, 'products:delete')

  return (
    <div>
      {canCreate && <button>Add Product</button>}
      {/* render table with role-gated actions */}
    </div>
  )
}
```

### 9e. Mutation with Server Actions

Mutations call Server Actions (not fetch). After success, invalidate the relevant query keys.

```ts
// hooks/mutations/use-void-sale.ts
'use client'
import { useMutation, useQueryClient } from '@tanstack/react-query'
import { voidSale } from '@/actions/sales'

export function useVoidSale() {
  const queryClient = useQueryClient()

  return useMutation({
    mutationFn: (saleId: string) => voidSale(saleId),
    onSuccess: () => {
      // Invalidate so the sales list re-fetches
      queryClient.invalidateQueries({ queryKey: ['sales'] })
    },
  })
}
```

```ts
// hooks/mutations/use-adjust-stock.ts
'use client'
import { useMutation, useQueryClient } from '@tanstack/react-query'
import { adjustStock } from '@/actions/inventory'

export function useAdjustStock() {
  const queryClient = useQueryClient()

  return useMutation({
    mutationFn: ({
      productId,
      quantity,
      reason,
    }: {
      productId: string
      quantity: number
      reason: string
    }) => adjustStock(productId, quantity, reason),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['inventory'] })
      queryClient.invalidateQueries({ queryKey: ['products'] })
    },
  })
}
```

### 9f. Query Key Conventions

Use a consistent, hierarchical key structure so invalidations are surgical:

```ts
// All products for a business
queryKey: ['products', businessId]

// Single product
queryKey: ['products', businessId, productId]

// Sales — scoped by role filter
queryKey: ['sales', businessId, { cashierId: userId }]   // CASHIER
queryKey: ['sales', businessId]                           // OWNER/MANAGER

// Inventory
queryKey: ['inventory', businessId]
queryKey: ['inventory', 'movements', businessId]

// Customers
queryKey: ['customers', businessId]
queryKey: ['customers', businessId, customerId]

// Credits
queryKey: ['credits', businessId]
queryKey: ['credits', businessId, { customerId }]

// Reports
queryKey: ['reports', 'sales', businessId, { from, to }]
queryKey: ['reports', 'inventory', businessId]

// Notifications
queryKey: ['notifications', userId]
```

## 10. `PermissionGate` Component

A reusable wrapper to hide/show UI based on role — do not use this as a security boundary (that's the DAL), but as a UX convenience.

```tsx
// components/shared/PermissionGate.tsx
'use client'
import { useRole } from '@/components/providers/RoleProvider'
import { hasPermission, canAny } from '@/lib/permissions'
import type { Permission } from '@/lib/permissions'

interface Props {
  permission?: Permission
  anyOf?: Permission[]
  children: React.ReactNode
  fallback?: React.ReactNode
}

export function PermissionGate({ permission, anyOf, children, fallback = null }: Props) {
  const { role } = useRole()

  const allowed = permission
    ? hasPermission(role, permission)
    : anyOf
    ? canAny(role, anyOf)
    : false

  return allowed ? <>{children}</> : <>{fallback}</>
}
```

Usage:

```tsx
<PermissionGate permission="sales:void">
  <Button onClick={() => voidSale(id)}>Void Sale</Button>
</PermissionGate>

<PermissionGate anyOf={['reports:full', 'reports:limited']}>
  <ReportsLink />
</PermissionGate>
```

## 11. `RoleProvider` — Client-Side Role Context

```tsx
// components/providers/RoleProvider.tsx
'use client'
import { createContext, useContext } from 'react'
import type { UserRole } from '@/generated/prisma'

interface RoleContextValue {
  role: UserRole
  user: {
    id: string
    name: string | null
    email: string
    businessId: string | null
  }
}

const RoleContext = createContext<RoleContextValue | null>(null)

export function RoleProvider({
  role,
  user,
  children,
}: RoleContextValue & { children: React.ReactNode }) {
  return (
    <RoleContext.Provider value={{ role, user }}>
      {children}
    </RoleContext.Provider>
  )
}

export function useRole() {
  const ctx = useContext(RoleContext)
  if (!ctx) throw new Error('useRole must be used within RoleProvider')
  return ctx
}
```

## 14. Key Rules — Summary for AI

1. **`proxy.ts`** — cookie existence check only. Named export `proxy`. No Prisma. No role check.
2. **`layout.tsx`** — calls `auth.api.getSession()`. Redirects wrong roles. One layout per route group that needs a gate.
3. **`lib/dal.ts`** — `getSession` and `requireRole` wrapped in React `cache()`. Import `'server-only'` at top. Called inside every Server Action and Route Handler.
4. **Server Actions** — always call `requireRole()` as the first line. `businessId` and `userId` always sourced from session, never from client input.
5. **TanStack Query** — Server Components prefetch with `getQueryClient()` + `prefetchQuery()`, pass `dehydrate(queryClient)` to `<HydrationBoundary>`. Client Components call `useQuery()` with the same key — data is already in cache, no spinner.
6. **`QueryClient`** — use `cache()` from React on the server to ensure one instance per request. Use `useState` on the client to ensure one instance per component lifecycle.
7. **`PermissionGate`** — UX only. Never treat it as a security boundary.
8. **`lib/permissions.ts`** — the single source of truth. `hasPermission(role, permission)` used everywhere.
9. **Mutations** — call Server Actions from `useMutation`, invalidate query keys on success.
10. **`businessId` scoping** — every Prisma query must include `businessId: session.user.businessId` to prevent cross-tenant data leaks.
